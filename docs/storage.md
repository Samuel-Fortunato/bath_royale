Current schema is v6. ## Architecture and durability (Phase 2.2A)

The application retains Provider, ChangeNotifier, SQLite (`sqlite3` 3.x), Material 3 and the locked Nix environment. `path_provider` locates the private application-support `bath_royale.sqlite`; SQLite native assets are bundled on Linux and Android. Tests use memory databases or private temporary files, never the production opener.

`AppState` validates local ownership and domain invariants and presents observable state/derived queries. One `BathroomRepository` at its action boundary delegates local loads, first-run initialization and explicit mutation transactions to `LocalStore`. SQL, serialization, schema management and connection ownership remain in `LocalStore`. There is no ORM or second reactive framework. The optional test-only HTTP transport is described below. Optional namespace/outbox/coordinator boundaries are described below; account association is absent.

Each action uses targeted INSERT/UPDATE/DELETE statements under `BEGIN IMMEDIATE`/`COMMIT`: bathroom creation/modification, visit registration/undo/removal, review creation/editing, favourites and theme. Direct-review visit+review insertion and confirmed visit+review deletion commit atomically. Review edits update content only and guard immutable identity/associations/creation time and monotonic update time. Bathroom edits preserve creator and provenance. Favourite actions persist an explicit boolean rather than retrying a toggle. No ordinary action deletes/reinserts a snapshot. Notifications, rebuilds, getters, rankings and other reads cause no persistence writes.

Successful commits precede applying in-memory changes and successful mutation notifications. A failed transaction rolls back, retains the previous observable domain state and stores one pending action's exact payload, IDs, timestamps and apply callback in memory. `storageError` notifies the existing blocking retry screen; this notification does not announce a successful mutation. Further actions are rejected until explicit retry succeeds. Retry re-executes the same transaction and then applies/notifies exactly once; retry without a pending action is a no-op. Entity-returning APIs reserve the identity on failure; their return alone is not proof of persistence. UI success navigation and visit celebration await `persistenceComplete`, which remains pending across failed retries. The existing Portuguese failure screen remains unchanged.

Pending input is **not durable across process termination**: keep the process open until retry succeeds, as the existing screen instructs. Committed data survives restart. This is a synchronous single-connection/single-application-instance boundary, not itself crash-durable pending work. The optional outbox below only covers successfully committed, explicitly eligible account mutations; background execution is absent. Do not attach throwing domain work to the post-commit apply callbacks; validation belongs before persistence.

First-run fixtures use a separate `initialize` transaction: insert fictional bathrooms and related records, settings and initialization marker together. A failed seed transaction leaves no partial fixture/marker and can be retried. An initialized database, including an intentionally empty one, is never reseeded; deleted samples never reappear. The six fictional bathrooms include reviewed/unreviewed visits, varied ratings/tags/comments/identities and a favourite, with discovered and undiscovered entries. Profile/Settings retains the fictional-data notice.

## Schema v5 and non-destructive migration

Ordered migrations and foreign-key validation execute within a single transaction. v1 defines relational entities/metadata; v2 adds theme settings; v3 adds deterministic emoji/accent identities; v4 adds comments and converts string tags into structured emoji/label snapshots; **v5 adds constrained provenance columns** to bathrooms, visits, reviews and favourites. v4 content is not reserialized or rewritten by v5. Entity IDs, relationships, timestamps, ratings, identities, tag JSON, comments, favourites and settings survive unchanged.

v5 defaults existing rows to `unclassified_legacy`, then marks stable bathroom seed IDs `0`–`5` and every associated visit/review/favourite `demo`, irrespective of edited names, authors, comments or UUID-shaped child IDs. Other historical prototype records remain unclassified. First-run fixtures are explicitly demo. New bathrooms created through state actions are `user_created`; related local records inherit the bathroom/visit restriction. New children of a future `remote` catalogue entry are locally authored (`user_created`). Edits never promote existing provenance. No remote records are imported in this milestone.

`Provenance.allowsFutureUpload` is a necessary local gate only: demo, unclassified legacy and remote cache rows are excluded; user-created rows still require future explicit account/product/publication policy. No application record is queued or uploaded; only explicit account test contexts exercise eligible queueing. This flag prevents accidents; it is not server-side proof of truth. See [data semantics](data-model.md).

Foreign keys are enabled on every connection. Unique IDs, normalized bathroom names, visit tuples and favourite pairs, the unique review-to-visit association and composite `(visit,bathroom,author)` foreign key remain intact. Rating/category bounds, timestamp ordering and boolean checks remain enforced. Timestamps use UTC microseconds; new entity IDs use UUID v4. Rapid repeat registration within the existing 800 ms guard reuses the last committed visit.

Unsupported future schemas, unknown nonempty unversioned databases, corrupt data and migration/integrity errors are refused without deleting the database. Failed migrations roll back schema, content and `user_version`; startup exposes the existing recoverable retry screen. No destructive reset is permitted for 2.2A. For manual recovery preserve the original database and any journal before repairs. Normal restarts and compatible updates always preserve data. Proper non-destructive migrations remain required before real users.

## Phase 2.2B — v6 namespaces and synchronization state

The ordered v5→v6 migration adds scope binding, outbox/dependencies, acknowledged server revisions, canonical remote records/tombstones, conflicts, opaque pull checkpoints and per-feed retry state. It never rebuilds or rewrites existing entity/settings tables. Distributed v5 files are bound to local guest only, including all fictional and unclassified content. No account mapping is inferred.

`openLocalStore(namespace: ...)` derives a stable file path and validates its persisted scope. Existing application calls retain the original guest path. Every account/environment and each environment's shared public cache has a separate database. Public caches cannot be used as mutation repositories. No cross-file joins, fallback reads, guest import or automatic account bootstrap exist. Namespace file separation is logical isolation, not credential storage or encryption.

Eligible test repositories atomically commit exact operation snapshots with local actions. Guest/default repositories, seeds, cache pulls, themes, ordinary reads and notifications never enqueue. Revisions/cache are separate from local domain drafts. Tombstones prevent stale resurrection; pull page/checkpoint/revision/retry clearing is atomic. Scoped coordinator requests invalidate results after switch/logout/expiry; original-account unsent work stays durable. See the [design](backend/client-synchronization.md) for implemented retry/error semantics, memory-only versus committed failures, protocol limits and 2.2C requirements.

`test/sync_test.dart` covers v5 preservation, cross-account/environment/public/guest files, atomic outbox/compound actions/deletions, restart/lost acknowledgment/duplicate receipts, bounds/dependencies, session changes and expiry, conflicts, stale deletes, pull rollback/checkpoints, provenance exclusions and no ordinary UI queueing. Existing regressions remain intact, with only current-schema assertions updated. Final executed verification is in [ROADMAP.md](../ROADMAP.md).


## Phase 2.2C — Real protocol verification

SQLite remains v6 with unchanged domain tables, provenance and namespace binding. Review acknowledgments now advance both review and parent visit revisions in one transaction, matching server CAS for confirmed deletion. Public visibility-removal markers may return at a higher revision; terminal identity tombstones cannot. Expired server cursors trigger bounded full-log replay into the separate cache, never a database reset or draft/outbox deletion. The explicitly injected HTTP transport is exercised against the new disposable local installation, including separate Dart processes and a server commit without local acknowledgment. The normal opener remains guest-only. See [server synchronization](backend/server-synchronization.md) for actual contracts, verification, Unicode compatibility gate and deferred production policies.


## Phase 2.3A — Offline account state ownership

Schema v6 and existing guest migration/seeding remain unchanged. Explicit `AppState.restoreAccountForTesting` initializes account files with empty domain lists and their stable subject, never sample defaults. The test-only scope owns and closes a selected state/connection; Provider replacement remounts routes/listeners, while session loss hides and retains open editors. Selection/disposal rejects open editor leases or failed pre-commit actions; delayed store opens cannot replace a newer session/selection. A failed open preserves the old state and files. `LocalStore.close` is idempotent; coordinators ignore results targeting retired connections.

Committed account data/settings/outboxes survive logout, switching and restart in the original namespace. Authentication does not authorize outbox creation, synchronization or guest association. Draft controllers and failed pre-commit callbacks remain memory-only, protected during test transitions but not durable across process death. No production retention/removal policy is chosen. See [offline accounts and production gates](backend/offline-accounts.md) for exact lifecycle, credential and composition boundaries.
