# A5.1 — Alpha release preparation

Status: implementation and isolated rehearsal only. A4 and A4.1 are owner-accepted. **No managed project access, deployment or configured APK publication is authorized by this document.** Deployment and publication require the owner's next approval. Existing managed state has not been inspected during A5.1.

## Approved alpha policy

Users download one universal APK from GitHub Releases, register in the app and sign in. No invitation, allowlist, manual account creation or public profile is required. Anonymous access remains read-only except for the narrowly scoped text-feedback submission RPC. Bathroom creation still requires its separate administrator-granted entitlement. There is no achievement/power-up acquisition system.

Email is an unverified account label. An automatically populated `email_confirmed_at` when confirmation is disabled is **not evidence of mailbox ownership**. Do not use it for support identity checks, granting privileges or account recovery. Production confirmation, email-link handling and SDK recovery remain available under the ordinary configuration, separately from `BATH_PUBLIC_ALPHA`.

The app now sends the current password with password changes. The server must enforce **Require Current Password**, not merely trust the form. Supabase Auth exempts recovery sessions from this check; therefore the alpha must also enable the Send Email hook `public.alpha_no_email`, which rejects recovery, OTP/magic-link and other email-auth delivery. Hiding the recovery form alone is insufficient. Disable phone, anonymous Auth accounts, OAuth and unused providers. Do not enable an alternative token-generation/recovery path for public clients.

References: [password security](https://supabase.com/docs/guides/auth/password-security), [pinned Auth password enforcement](https://github.com/supabase/auth/blob/v2.198.0/internal/api/user.go), [free-plan SQL Auth hooks](https://supabase.com/docs/guides/auth/auth-hooks), [Send Email hook](https://supabase.com/docs/guides/auth/auth-hooks/send-email-hook), [Auth rate limits](https://supabase.com/docs/guides/auth/rate-limits).

## Abuse limits and free-plan operation

Configure native Auth rate limits for signup/verification at 30 requests per five minutes per IP, token endpoints at 150 per five minutes per IP, with the provider's token-bucket burst limits. The SQL Before User Created hook `public.alpha_signup_limit` adds a global 100 accepted signup attempts per UTC day and a 3,000 retained-account ceiling. Attempts can consume capacity even if a later signup fails. These conservative ceilings may require an explicit operator review; they do not restrict registration to particular people. Hook errors fail closed. SQL counter pruning retains at most 30 days of counters.

Existing feedback constraints remain: exact idempotent retries, bounded descriptions and metadata, 30 reports/hour, 100/day and 5,000 retained reports globally, transactional serialization, administrator-only reading/status changes and no anonymous table access. This limits storage even when a client rotates report IDs. A determined attacker can exhaust these global quotas; they are not a claim of complete denial-of-service protection. Inspect ordinary Supabase usage/rate-limit metrics before changing limits. No paid services, CAPTCHA subscription, external analytics or separate backend are introduced. Free-plan limits and possible project pausing mean this is not an always-on service commitment.

## Private recovery and deletion

Initial-alpha support is shown through `lib/auth/alpha_policy.dart`. The owner's personal email is approved **only for the initial alpha**. A mandatory public-launch gate replaces it with a dedicated project support contact in the app, privacy notice, documentation and release materials; scan both source and built artifacts before that launch. Do not publish the withdrawn telephone contact.

While signed in, Settings → account management → **Guardar código de recuperação** asks for the current password. A temporary SDK client performs fresh password authentication without replacing the main session. The server checks a signed password-authenticated session created within five minutes, generates a 256-bit random credential and stores only its SHA-256 digest. A replacement invalidates the old code. Save the displayed `account-UUID:secret` outside the phone; it is revealed once, never logged or saved by the app. Anyone possessing it can prove control, so handle it like a password. Native current-password enforcement applies independently to ordinary password changes.

Operator recovery procedure, after deployment approval:

1. Receive the code through the approved private support channel. Never request a password, access token, complete history or screenshot of account security. Email access, a claimed address, name or friendship alone is insufficient.
2. In a private, non-logging operator session use a bound SQL parameter: `SELECT app_private.consume_alpha_recovery($1);`. It atomically consumes the matching digest and returns the **exact account UUID**. No anon/authenticated/service-role client may execute it. Do not paste secrets into a public SQL issue, shell history or CI logs. Keep a private short-lived verified case if the subsequent reset fails; do not restore/replay a consumed code.
3. Use Supabase Auth Admin `updateUserById(UUID, {password: <new random temporary password>})` from a private operator tool/session. The service credential must stay outside Git, APKs, public repository variables and user devices. Never edit encrypted password hashes directly. Revoke all refresh sessions for that UUID (`DELETE FROM auth.sessions WHERE user_id=$1` in the private operator transaction); existing access JWTs can remain valid until their configured expiry. Deliver the temporary password only in the same proven private conversation, then ask the user to change it and generate a replacement recovery code.
4. If the password and recovery code are both lost, recover access on an already authenticated device by fresh password proof if possible. Otherwise ownership cannot be established safely: refuse reassignment based only on the unverified email. A new account is possible, but private history cannot be promised. Preserve existing records pending an actual proven request.

For deletion, first require fresh authenticated proof/current password, or consume a recovery code as above. Identify by verified UUID, never an unverified email lookup alone. Quiesce application writers, take a private backup, then call operator-only `SELECT app_private.erase_alpha_domain($1::uuid);`. It removes private history, favourites, reviews, profile, reports, privileges, recovery proof and private synchronization records. It keeps shared bathroom identities and other accounts' history, strips the erased contributor attribution and retains public removal markers. Legacy cross-account/private references cause an error requiring individual review; never work around this with cascading resets. Attribution guards are disabled and restored **inside the same transaction**, with all other publication/change triggers retained; any error rolls back. Quiescence avoids concurrent-write lock contention.

After domain erasure succeeds, use native Auth Admin `deleteUser(UUID)` and verify no Auth user remains. Keep a minimal private erasure ledger (UUID and deletion time only) until all affected backups expire, so a restoration reapplies erasures before reopening. Feedback is intentionally not linked to an account: locate a specifically identified report privately if a proven request includes its report ID/content; do not guess ownership from text. Offline devices may retain previously downloaded data until reconnecting or local removal. Deleted accounts cannot upload remaining local operations. Backups cannot be claimed to disappear instantly.

Proposed initial-alpha operating policy, requiring owner approval before admitting real data: keep live account data until proven deletion, remove reviewed feedback within 90 days, encrypt a rolling seven-day daily backup and erase expired backups and expired support cases. These periods are operational proposals, not a legal-compliance statement. Record the approved periods and reflect them accurately in the privacy notice before distribution. No scheduled paid job is required; the operator must actually perform and record the routine.

## Non-destructive deployment checklist — approval gate

These are the exact next actions **after** owner deployment approval, using the existing managed Free project and its ordinary HTTPS origin. Do not execute historical `cloud_rehearsal.py`: its managed fixture-writing entry points are now retired and fail before connecting. Disposable local test resets remain confined to isolated instances.

1. Temporarily quiesce existing writers and signup while taking inventory. Retain the existing private connection/API state outside Git (0700 directory, 0600 files, verified PostgreSQL TLS). Inspect actual migration ledger/checksums, schema, RLS/grants, Auth users, providers/hooks, catalogue and existing fictional test records. Do not infer current managed contents from old documentation.
2. Export a private backup using the existing `backend/cloud_transfer.py export --source-state "$SOURCE_STATE" --project "$PROJECT_REF" --bundle "$BUNDLE" --quiesced` under `nix develop .#backend`. That tool enforces the retained project and verified TLS. It does not run fixtures. **If the older managed schema lacks current tables, take a native schema/data/Auth logical backup first and reconcile the version before using the current allowlist; do not bypass a failed export.** Verify checksums and restore the bundle in a fresh isolated local target before modifying managed data. Retain an encrypted copy outside the checkout and keep decryption material separately.
3. Generate the ordered plan locally: `python3 backend/release_plan.py --output /tmp/bath-alpha-plan.sql`. Review all migrations `001` through `016`. The plan uses one transaction, advisory lock, immutable SHA-256 ledger checks and schema reload; already applied matching migrations are skipped. It never resets tables or imports fixtures. Unknown/untracked existing objects or checksum differences require reconciliation, not editing old migrations or pretending they were applied.
4. With writers still quiescent, execute the reviewed plan through `psql -X -f /tmp/bath-alpha-plan.sql` in the private verified-TLS connection environment described in `cloud-transfer-tooling.md`. Do not place credential-bearing URLs in command arguments/history. Stop on the first error; the transaction rolls back. Preserve evidence and investigate instead of resetting.
5. Handle fictional managed data **by explicit reviewed identifiers only** after backup. Do not run the development seeder, mass truncate, delete all Auth users or overwrite owner test activity. Archive/hide known fictional catalogue rows and remove their published review projections through the protected moderation/domain path. Revoke old experimental entitlements, identify old fictional Auth accounts and retire them through the verified deletion procedure only when confirmed disposable. Old queued clients must no longer be able to republish retired fixtures. If classification is uncertain, keep exposure closed and ask the owner. A new account/empty catalogue is preferable to pretending fixtures are genuine.
6. Set Auth to open email/password signup, confirmation OFF for alpha, minimum password eight characters, secure refresh rotation ON, current-password enforcement ON, short access JWT expiry (300 seconds), native rate limits above, and both SQL hooks ON. Remove unused providers, email recovery/magic-link delivery and stale recovery tokens/sessions left by experimental settings. Revoke retained old refresh sessions before exposure; wait out old access-token lifetimes. Verify hooks with actual disposable HTTP requests against the deployment before publishing. If managed Auth does not offer effective current-password enforcement and both hooks on Free, **block release** rather than weakening protections.
7. Expose only the existing public application RPC surface. Keep `app_private` unexposed; anon can read the public catalogue/anonymous published-review projection and submit bounded feedback only. No raw private table writes/reads, operator recovery/erasure or moderator/entitlement RPC access. Verify RLS and direct API attacks using an anonymous client and two independent ordinary accounts, plus a separate admin. Review effective function grants/default privileges, not just UI visibility. Run the same entitlement, moderation, feedback quota, historical-feed privacy and account-isolation cases rehearsed locally.
8. Provision the first administrator by **verified account UUID**: owner registers normally in the app, performs fresh password sign-in and proves that account in the private operator session. Insert that exact UUID into `app_private.moderators(user_id)` and, separately if needed, `app_private.bathroom_creators(user_id)` with `ON CONFLICT DO NOTHING`. Never grant based only on an unverified email string or user-editable metadata. Confirm ordinary accounts cannot grant themselves capabilities. Secure the Supabase/GitHub operator accounts with their own MFA; no administrative credential ships in the app.
9. The owner separately prepares the genuine bathroom catalogue, standard Portuguese review tags and suggested emoji sets. Grant catalogue creation to the owner and create only verified genuine entries through the app, checking location/name/duplicates. Official/community classification must reflect actual verification, not synthetic popularity. Launching with an empty catalogue is supported; do not fabricate genuine bathrooms/reviews. See `docs/content-maintenance.md` for independent suggestion maintenance and legacy-identity precautions.
10. Approve retention/support/privacy wording, take a post-migration backup and repeat restoration/permission checks. Confirm real offline/reconnection, secure restart and second-device behavior on the managed configuration. Only then authorize configured APK publication.

## Backup and restoration

Use `cloud_transfer.py export`, `restore` and `verify` as documented in [the transfer operations](cloud-transfer-tooling.md). The current allowlist includes recovery **digests**, signup quota counters, private feedback, application rows, Auth users/identities, immutable receipts/cursors/change feeds and the sequence/migration ledger. These bundles contain password hashes/private data: keep them outside Git/Actions artifacts and encrypt storage. Session/refresh tokens are deliberately not restored; users sign in again. Storage screenshots are not implemented. Do not replay exported role grants unreviewed into managed Supabase.

A5.1 rehearses logical schema/data restoration in a separate local database and verifies exact rows, feed sequence, receipt replay, cursor continuation and clock collision behavior. For a real incident: quiesce writes, preserve the failed state, verify a chosen backup's checksums/version, restore first to a fresh isolated local instance, run preservation/authorization checks, reapply proven erasures and then plan an explicitly approved managed restoration. Never auto-delete the live project, reset local user stores or use a backend exception as permission to recreate data. Refresh sessions must be revoked; stable account UUIDs and the backend HTTPS origin must be preserved for existing client namespaces. Changed origin is a separately planned migration, not a transparent update.

## GitHub APK handover — publication approval gate

`.github/workflows/android-preview.yml` retains locked dependency checks, tests, original signing secret, certificate/package/version/universal AOT verification, SHA256SUMS, immutable exact-commit tags and resumable draft-first publication. Until the gate is enabled it continues publishing only **unconfigured previews**. The configured path uses `tool/build_alpha.py`, ordinary `lib/main.dart`, trusted system HTTPS, `BATH_PUBLIC_ALPHA=true` and alpha feedback ON. It excludes account selectors, fictional bootstrap data, local credentials/certificates and local TLS entry points, and scans actual APK payloads for their markers.

After deployment and publication are approved and all checks above pass:

1. Keep `ANDROID_PREVIEW_KEYSTORE_BASE64` as the existing Actions **secret**; never replace the signing identity. Its expected certificate is checked by `tool/verify_preview.py`. APK identity remains `com.example.bath_royale`. Android version code is `1000 + GITHUB_RUN_NUMBER`, monotonically increasing on this existing workflow; configured version names are `0.1.0-alpha.<code>`. Do not recreate the workflow/run numbering without a version-code migration.
2. Set repository **variables**, containing public configuration only: `SUPABASE_URL=https://<existing-project-ref>.supabase.co` and `SUPABASE_PUBLISHABLE_KEY=<public publishable or legacy anon key>`. Never set a service-role key, database URL/password, administrative key or signing material as a public variable. The build rejects secret keys and non-HTTPS/local endpoints.
3. **Only after owner approval**, set repository variable `ALPHA_RELEASE_APPROVED=true` and dispatch Android preview on the reviewed main commit. The build and verification must succeed before automatic publication. Alpha tags are `alpha-<code>`; ordinary previews remain `preview-<code>`. Publication uses the build's recorded mode, not a later variable change. Disabling the gate stops future configured builds; already published releases are never silently overwritten.
4. Download `bath-royale.apk` and `SHA256SUMS` from the resulting GitHub pre-release and verify `sha256sum -c SHA256SUMS`. Install on Android using **Atualizar**; permit browser installation if prompted. Keep the existing app installed, never clear data/uninstall, and use the same certificate and an equal/higher version code. One universal APK covers supported architectures; no extra distribution service/domain is necessary.

The locally rehearsed configured artifact is private at `/tmp/bath-a51-prepared/` (ephemeral, not a release asset). Building it used only retained **public configuration**, without contacting the managed endpoint. It is not proof that managed deployment works. The phone receives the separately compiled isolated **development** target only. Rebuild from the final reviewed commit and a fresh workflow code for actual publication.
