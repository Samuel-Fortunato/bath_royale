## Approved alpha policy

Users download one universal APK from GitHub Releases, register in the app and sign in. No invitation, allowlist, manual account creation or public profile is required. Anonymous access remains read-only except for the narrowly scoped text-feedback submission RPC. Bathroom creation still requires its separate administrator-granted entitlement. There is no achievement/power-up acquisition system.

Email is an unverified account label. An automatically populated `email_confirmed_at` when confirmation is disabled is **not evidence of mailbox ownership**. Do not use it for support identity checks, granting privileges or account recovery. Production confirmation, email-link handling and SDK recovery remain available under the ordinary configuration, separately from `BATH_PUBLIC_ALPHA`.

The app now sends the current password with password changes. The server must enforce **Require Current Password**, not merely trust the form. Supabase Auth exempts recovery sessions from this check; therefore the alpha must also enable the Send Email hook `public.alpha_no_email`, which rejects recovery, OTP/magic-link and other email-auth delivery. Hiding the recovery form alone is insufficient. Disable phone, anonymous Auth accounts, OAuth and unused providers. Do not enable an alternative token-generation/recovery path for public clients.

References: [password security](https://supabase.com/docs/guides/auth/password-security), [pinned Auth password enforcement](https://github.com/supabase/auth/blob/v2.198.0/internal/api/user.go), [free-plan SQL Auth hooks](https://supabase.com/docs/guides/auth/auth-hooks), [Send Email hook](https://supabase.com/docs/guides/auth/auth-hooks/send-email-hook), [Auth rate limits](https://supabase.com/docs/guides/auth/rate-limits).

## Abuse limits and free-plan operation

Configure native Auth rate limits for signup/verification at 30 requests per five minutes per IP, token endpoints at 150 per five minutes per IP, with the provider's token-bucket burst limits. The SQL Before User Created hook `public.alpha_signup_limit` adds a global 100 accepted signup attempts per UTC day and a 3,000 retained-account ceiling. Attempts can consume capacity even if a later signup fails. These conservative ceilings may require an explicit operator review; they do not restrict registration to particular people. Hook errors fail closed. SQL counter pruning retains at most 30 days of counters.

Existing feedback constraints remain: exact idempotent retries, bounded descriptions and metadata, 30 reports/hour, 100/day and 5,000 retained reports globally, transactional serialization, administrator-only reading/status changes and no anonymous table access. This limits storage even when a client rotates report IDs. A determined attacker can exhaust these global quotas; they are not a claim of complete denial-of-service protection. Inspect ordinary Supabase usage/rate-limit metrics before changing limits. No paid services, CAPTCHA subscription, external analytics or separate backend are introduced. Free-plan limits and possible project pausing mean this is not an always-on service commitment.

## Private recovery and deletion

Initial-alpha support is shown through `lib/auth/alpha_policy.dart`. The owner's personal email is approved **only for the initial alpha**. A mandatory public-launch gate replaces it with a dedicated project support contact in the app, privacy notice, documentation and release materials; scan both source and built artifacts before that launch. Do not publish the withdrawn telephone contact.

While signed in, Settings → account management → **Guardar código de recuperação** asks for the current password. A temporary SDK client performs fresh password authentication without replacing the main session. The server checks a signed password-authenticated session created within five minutes, generates a 256-bit random credential and stores only its SHA-256 digest. A replacement invalidates the old code. Save the displayed `account-UUID:secret` outside the phone; it is revealed once, never logged or saved by the app. Anyone possessing it can prove control, so handle it like a password. Native current-password enforcement applies independently to ordinary password changes.

Operator recovery procedure, after deployment approval:

1. Receive the code through the approved private support channel. Never request a password, access token, complete history or screenshot of account security. Email access, a claimed address, name or friendship alone is insufficient.
2. In a private, non-logging operator session use a bound SQL parameter: `SELECT app_private.consume_alpha_recovery($1);`. It atomically consumes the matching digest and returns the **exact account UUID**. No anon/authenticated/service-role client may execute it. Do not paste secrets into a public SQL issue, shell history or CI logs. Keep a private short-lived verified case if the subsequent reset fails; do not restore/replay a consumed code.
3. Use Supabase Auth Admin `updateUserById(UUID, {password: <new random temporary password>})` from a private operator tool/session. The service credential must stay outside Git, APKs, public repository variables and user devices. Never edit encrypted password hashes directly. Revoke all refresh sessions for that UUID (`DELETE FROM auth.sessions WHERE user_id=$1` in the private operator transaction); existing access JWTs can remain valid until their configured expiry. Deliver the temporary password only in the same proven private conversation, then ask the user to change it and generate a replacement recovery code.
4. If the password and recovery code are both lost, recover access on an already authenticated device by fresh password proof if possible. Otherwise ownership cannot be established safely: refuse reassignment based only on the unverified email. A new account is possible, but private history cannot be promised. Preserve existing records pending an actual proven request.

For deletion, first require fresh authenticated proof/current password, or consume a recovery code as above. Identify by verified UUID, never an unverified email lookup alone. Quiesce application writers, take a private backup, then call operator-only `SELECT app_private.erase_alpha_domain($1::uuid);`. It removes private history, favourites, reviews, profile, reports, privileges, recovery proof and private synchronization records. It keeps shared bathroom identities and other accounts' history, strips the erased contributor attribution and retains public removal markers. Legacy cross-account/private references cause an error requiring individual review; never work around this with cascading resets. Attribution guards are disabled and restored **inside the same transaction**, with all other publication/change triggers retained; any error rolls back. Quiescence avoids concurrent-write lock contention.

After domain erasure succeeds, use native Auth Admin `deleteUser(UUID)` and verify no Auth user remains. Keep a minimal private erasure ledger (UUID and deletion time only) until all affected backups expire, so a restoration reapplies erasures before reopening. Feedback is intentionally not linked to an account: locate a specifically identified report privately if a proven request includes its report ID/content; do not guess ownership from text. Offline devices may retain previously downloaded data until reconnecting or local removal. Deleted accounts cannot upload remaining local operations. Backups cannot be claimed to disappear instantly.

The owner approved the initial-alpha operating policy for A5.3: retain account data until proven deletion, remove reviewed feedback after 90 days, resolved support cases after 30 days, and maintain encrypted daily backups with rolling seven-day retention. Keep the minimal erasure ledger until affected backups expire. See [manual operations and responsibilities](alpha-operations.md). These are operational duties, not a legal-compliance statement or a claim of scheduled automation.

## Backup and restoration

Use `cloud_transfer.py export`, `restore` and `verify` as documented in [the transfer operations](cloud-transfer-tooling.md). A5.1 rehearses logical schema/data restoration in a separate local database and verifies exact rows, feed sequence, receipt replay, cursor continuation and clock collision behavior. For a real incident: quiesce writes, preserve the failed state, verify a chosen backup's checksums/version, restore first to a fresh isolated local instance, run preservation/authorization checks, reapply proven erasures and then plan an explicitly approved managed restoration. Never auto-delete the live project, reset local user stores or use a backend exception as permission to recreate data. Refresh sessions must be revoked; stable account UUIDs and the backend HTTPS origin must be preserved for existing client namespaces. Changed origin is a separately planned migration, not a transparent update.
