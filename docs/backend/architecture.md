## Recommendation and comparison

**Candidate accepted for the local PoC; production conditional:** evaluate Supabase/PostgreSQL first, preserving Flutter, Provider, Material 3 and SQLite. Permit community rollout only after the [portability acceptance gate](portability.md#migration-acceptance-gate-before-production-users) passes. Do not create a hosted project during this milestone. A documented export path alone does not meet the owner's requirement for a verified exit. See [decision record](decision-0001.md).

The operational judgments in this table are project-specific inferences from the linked official documentation, not benchmarks.

| Candidate | Operations and ongoing cost | Data, authentication and authorization | Portability and fit |
| --- | --- | --- | --- |
| Supabase / PostgreSQL | Managed Free minimizes initial administration; quotas, pausing and email delivery require planning. Self-hosting shifts upgrades, backups, security and uptime to the owner. | SQL constraints, transactions and RLS fit bathrooms, visits and author-owned reviews. Auth supplies password and OAuth flows. | Standard SQL helps preserve the relational model; Supabase Auth/configuration still requires a tested migration. Preferred if the exit gate passes. |

Appwrite Free allows two projects, applies shared organization limits and restricts services when limits are reached. Inactive Free projects pause after seven days and paused projects can be deleted after 90 days. Thus it also needs an independent backup/exit plan. Dedicated PostgreSQL appears as a paid compute option on current pricing; it must not be assumed to be the free TablesDB offering. Remaining entirely local has the least operational burden and remains the fallback while these gates are unresolved. A custom PostgreSQL API would give control but would make the owner maintain authentication/API code; it is not recommended for this AI-assisted development workflow.

## Existing boundaries — verified by code inspection

| Location | Current responsibility | Remote-integration implication |
| --- | --- | --- |
| `lib/main.dart`, `storage/open_store.dart` | Open the native application-support SQLite file, restore state, expose startup retry without deleting data. | Keep startup/offline access independent of the network. Native opener is not web-compatible. |
| `state/app_state.dart` | `ChangeNotifier`, in-memory entity lists, ownership/integrity checks, UUID v4 generation, mutations and derived views. `notifyListeners()` synchronously saves the entire snapshot, including theme changes. | Local ownership is not authentication. Never trigger remote writes from notification or widget rebuilds. |
| `storage/local_store.dart` | Explicit SQL, schema v4, ordered migrations, foreign keys, checks, serialization and transactional snapshot replacement. | Replace full-table delete/reinsert saves with incremental transactions before synchronization. Local writes and outbox entries must commit together. |
| `models/` | Distinct Bathroom, Visit, Review and favourite records; review-to-visit ownership and unique association. | Retain domain semantics; add transport conversion at the remote boundary. |
| `pages/`, `widgets/` | Provider reads/actions; rankings and collection derived locally. | Keep existing navigation, humorous rating descriptions and Portuguese (Portugal) text. Community aggregates will require a separately approved data scope. |
| `state/sample_data.dart` | Six bathrooms with IDs `0`–`5`, sample reviews/visits, `local-user`; restore adds an unreviewed sample visit and favourite. | No trustworthy per-record provenance or real account mapping currently exists. UUID-shaped IDs alone do not prove genuine content. |

Current reviews have structured emoji/label tags, an optional 500-grapheme comment, scores 0–5 / paper 0–2 / other categories 0–4, immutable associations and edit timestamps. One visit has at most one review; repeated visits may each have a review. Dates persist as UTC microseconds. Favourites are per-user flags; discoveries and latest visits are derived. Local “community” means all reviews in the local database, not a shared catalogue. See [model](../data-model.md) and [storage](../storage.md).

## Minimal proposed boundaries

Introduce one small `BathroomRepository` at the existing state action boundary when remote work starts. It owns local queries and durable mutation transactions; `LocalStore` remains the SQLite implementation detail. Add a `SupabaseDataSource` for explicit API calls, an `AuthSession` adapter for account/session events and a single `SyncCoordinator` for the durable outbox and pull cursors. Inject these through existing Provider/bootstrap wiring. Do not add a second state framework, ORM, generic repository per table, service locator or synchronization vendor.

`AppState` continues to present observable state and derived views. Successful local commits precede success notifications; preserve retry/error handling without losing committed or pending work. Introduce abstractions incrementally with behavior tests rather than refactoring the entire app now. Any future `supabase_flutter` or platform credential-storage dependency needs a focused implementation review; none is added here.

Proposed flow: UI → AppState → repository → SQLite (entity + outbox transaction); coordinator ↔ Supabase data source ↔ PostgreSQL. Network results enter SQLite transactionally, then update Provider. SQLite serves all normal screen reads.

## Proposed authority and privacy

| Data | Authority and publication |
| --- | --- |
| Theme and guest history/drafts | Local SQLite only. No account or network required. |
| Account-associated visits/favourites | PostgreSQL authoritative for acknowledged cross-device records; SQLite retains pending edits and an account-scoped offline copy. Cloud backup of private history should be opt-in, pending owner decision. |
| Bathroom proposals | Locally usable drafts; authenticated submission becomes a private pending proposal. Server approval creates/updates a public catalogue record. |
| Published bathrooms/reviews | Server authoritative for publication, revisions and moderation. SQLite is a cache plus private pending edits. Unsent edits must not overwrite canonical cached revisions. |
| Attribution and moderation | Server controlled; contributor identity remains distinct from later approver/editor identity. |

All published bathrooms are publicly discoverable. Private bathrooms remain excluded. Private visits are separate from public reviews: do not expose the visits table, exact visit timestamp, private visit ID, favourites or account email through public review endpoints. Use an explicit public projection containing review ID, bathroom ID, allowed public author identity, scores, tags, comment and approved publication metadata. The internal review/visit relationship remains available only to its author and appropriately authorized server code. Review publication inherently reveals some activity; the exact public identity/date policy requires owner approval.

Do not fetch every user's visits to construct the current `ExperienceDetailsPage`. Public review detail needs a review-based projection; own experience detail continues to resolve a private visit. Public aggregates must include only eligible published reviews, count one's own published review once, exclude pending/hidden material and retain current score semantics until a separate ranking decision.

## Proposed incremental synchronization

1. Continue working offline. Commit each real local action and a durable outbox operation in one SQLite transaction. Do not enqueue demo data, cache refreshes or theme changes. Account-required publication waits for login; losing a connection never discards a visit.
2. Assign UUID v4 entity IDs and an operation UUID once, persist them and reuse on every retry. Keep guest device/profile ID separate from `auth.users.id`. Existing text sample IDs cannot be cast blindly to PostgreSQL UUIDs; use an explicit mapping only for selected genuine imports.
3. Submit bounded batches in dependency order (proposal/catalogue mapping, private visit, optional review). A transactional server command derives ownership from the session and records `(account_id, operation_id)` with a payload fingerprint and result. Replaying the same request returns the same result; reusing an operation ID with a different payload fails. Unique visit/review constraints remain final guards. Atomic visit+review submission must not partially publish.
4. Use a server revision number and compare-and-set `base_revision` for edits; server timestamps order server changes, while `visited_at` retains experience chronology. Device clocks and `updatedAt` are not conflict arbiters. Keep a local draft on revision conflict, fetch the remote revision and require explicit resolution for review text/rating changes. Favourite commands set a boolean, never replay a toggle. Conflicting favourite writes follow accepted server order, subject to product confirmation.
5. Deletes create server tombstones and durable outbox operations. Delete a visit and its associated review atomically only with the existing explicit confirmation semantics. A stale edit cannot resurrect a deleted record. Retain tombstones through the supported offline window; expired cursors require a complete scoped refresh that preserves unsent drafts. Catalogue withdrawal preserves private visit references through a minimal unavailable-entry record. Retention and account-erasure policy require approval before production.
6. Pull separate public and own-private change feeds, including removals caused by moderation. Use an opaque committed checkpoint with bounded pagination and transactional local application/checkpoint advancement. Do not use a plain sequence allocated before commit as a reliable watermark: later commits can arrive out of order. Prove no gaps under overlapping commits in the PoC (or use overlapping server-time windows with ID/revision deduplication and periodic reconciliation). Advance acknowledgment only after durable local apply.
7. Run one sync at a time on foreground/resume, explicit retry and bounded backoff with jitter. Connectivity hints do not prove reachability. Pause on expired auth, retain the queue on quota/paused-server errors, and distinguish authorization rejection from retryable transport failure. Background execution, Realtime and automatic conflict merging are unnecessary initially.

## Guest association and fictional-data gate

Guest means local-only, not an automatically created Supabase anonymous account. Allow catalogue browsing with the public client role when available and preserve local use without sign-in. On an explicit account-association action, show a preview of genuine items eligible for private backup versus public submission. Bind selected records and operation IDs to the authenticated subject in one local transaction; retry idempotently. Never infer account identity from email strings or remap every `local-user` record.

Before any upload implementation, add provenance such as `demo`, `unclassified_legacy`, `user_created` and `remote` to local records plus the environment namespace. Mark all current seed IDs and related visits/reviews/favourites as demo, including modified samples and new visits linked to sample bathrooms. Conservatively classify other existing records as unclassified: this prototype has never promised genuine community content. Default-deny upload for both demo and legacy unknown data. Import requires explicit review and mapping to a real approved bathroom; it must never publish sample comments, authors or synthetic dates. Do not clear local data to achieve this separation.

The server cannot establish truth from a client provenance flag. Separate fictional test projects/fixtures from genuine catalogue initialization, reject known seed identities at the import endpoint, disallow bulk snapshot imports and moderate contributions. Test that account association, reinstall and retry cannot silently publish fiction. Provenance is an accidental-upload guard, not proof that an arbitrary user review is truthful.

## Authentication and server security proposal

Use Supabase Auth email/password for the fictional PoC; production sign-in method remains open because confirmation/recovery email needs an affordable delivery plan. OAuth is an option, not a requirement or a reason to buy a domain. Request PKCE for external/confirmation flows where supported, allow exact application redirects, and test Android deep links and Linux callbacks. Do not require university SSO without checking institutional access.

Persist refresh credentials through reviewed platform-protected storage, keep access tokens short lived, let the SDK refresh sessions, and handle refresh failure/revocation. Never put tokens into the SQLite snapshot, logs or source. An expired token leaves offline local use intact but cannot authorize remote work. On logout stop sync and separate/hide the account's cache from guest and other accounts. Keep unsent work bound to its original account; neither replay it as a newly signed-in user nor silently erase it. Device-data removal, reauthentication and shared-device expectations need product acceptance. Supabase documents access/refresh token sessions in [Auth sessions](https://supabase.com/docs/guides/auth/sessions).

Only a publishable/anon client key belongs in Flutter. Database passwords, secret/service-role keys and moderation credentials never do. Enforce grants and RLS on every exposed table: `USING` for reads/updates/deletes and `WITH CHECK` for insert/update ownership. Derive `owner_id` from `auth.uid()`, reject reassignment of author/bathroom/visit/creation identity, and enforce matching visit owner/bathroom plus one review per visit in SQL. UUID secrecy is not authorization. Supabase warns that privileged service keys bypass RLS; see [RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security).

Public grants expose only published projections. A public view must not accidentally inherit privileged access: explicitly review view security, column grants and security-invoker behavior. Private base tables and joins remain protected. Submission commands cannot grant approval or contributor rewards. Any necessary privileged SQL function must have a fixed search path, narrow execute grants, explicit subject checks and tests against direct API bypass. Administrative roles come from protected server records/claims, never editable user metadata. Apply input/rate limits and safe plain-text rendering; client validation remains helpful but insufficient.

## Future-compatible content — proposal, not implementation

Keep bathroom identity, institution/geography membership, origin/contributor and verification/publication state distinct. Inside/outside University of Aveiro presentation remains exploratory; do not encode Official/Community or campus categories as permanent exclusive enums now.

Initially retain structured review-tag snapshots with emoji/label and a versioned canonical key. Future approved tag catalogue IDs and aliases can be added without rewriting historic meanings. Preserve ten-tag/thirty-grapheme limits, equivalence rules and optional 500-grapheme plain-text review comments. PostgreSQL character length is not Dart extended-grapheme length: prove equivalent server validation or approve a documented bound; do not claim `char_length` alone is equivalent. Review comments are not a reply-thread system.

Reserve public contributor profiles separately from auth email/private preferences. Record original contributor and later moderation events independently. Future reporting, hidden/pending/approved states and audit trails must support author edits and takedowns without exposing private history. Reward only approved contributions; XP, achievements, recognition values and anti-abuse policy remain undecided and unimplemented. No production shared content should launch before moderation, privacy, deletion and attribution rules are approved and tested.
